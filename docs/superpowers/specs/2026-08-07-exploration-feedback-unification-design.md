# 探索反馈统一化设计规格

## 目标

补齐垂直切片中“发现 → 交互 → 解锁 → 奖励”的即时反馈，让玩家能在不依赖文字说明的情况下理解地标、机关、路径门和探索奖励的状态变化。

本轮只覆盖四类事件：地标发现、机关激活、路径门开启、探索奖励领取。反馈包括 Native 音效、HUD 短提示和现有震动桥接；不扩展完整音频资源系统，不让 ArkTS 自行推断探索状态。

## 设计

### 事件来源与快照

Loop 在探索状态发生成功变化的同一处生成一次性反馈事件，并写入 `GameSnapshot` 尾部字段：事件类型、事件 ID、事件持续毫秒数、事件标题和事件副标题。默认事件类型为无，持续时间递减到零后清空；事件字段不进入存档，避免加载后重复播放。

事件类型固定为：`None`、`PoiDiscovered`、`PuzzleActivated`、`GateOpened`、`RewardClaimed`。事件 ID 使用世界内容 ID，标题和副标题来自 `ExplorationContent` 配置及关联节点，不在 UI 中复制世界文案。

### 反馈映射

- 地标发现：发现提示音，HUD 显示“发现地标”和地标名，轻震动。
- 机关激活：共鸣短音效，HUD 显示“机关已激活”和机关名，轻震动。
- 路径门开启：阶段切换/低频开启音，HUD 显示“路径已开启”和门名，较强震动。
- 探索奖励：奖励音，HUD 显示奖励名及资源摘要，轻震动。

每个成功事件只触发一次。事件持续期间新事件覆盖旧事件，但同一逻辑 tick 不重复派发。

### ArkTS 边界

ArkTS 仅消费事件快照并显示一个统一 `ExplorationToast`，不访问 `ExplorationContent`，不判断机关是否开启，也不直接调用探索音效。事件为无时不渲染提示；事件结束时自然隐藏。

### 错误与兼容

失败交互不产生探索成功反馈，继续使用现有拒绝提示。新增快照字段只追加到 Native/Bridge/GamePage 链，默认值保持旧行为；V9 存档格式和字段顺序不变。

## 测试验收

- 纯逻辑测试验证四类事件的类型、ID、标题和一次性覆盖行为。
- Bridge 契约验证字段在 `GameSnapshot`、N-API、ArkTS Bridge、`Index.d.ts`、GamePage 和 HUD 中一致。
- 现有探索、存档、任务和 HAP 构建测试保持通过。
- 手动验收：连续完成机关、开门、奖励和地标发现时，四类提示与音效/震动各出现一次，加载存档不会重播旧事件。
